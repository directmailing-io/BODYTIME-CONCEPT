Lokales Setup

Voraussetzungen

Node.js 20+, npm oder pnpm, Git. Kein Docker notwendig fur lokale Entwicklung.

Repository klonen & installieren

git clone https://github.com/directmailing-io/BODYTIME-CONCEPT.git
cd BODYTIME-CONCEPT
npm install

.env.local anlegen

Die Datei .env.local liegt im Gitignore und muss lokal manuell angelegt werden. Werte vom Auftraggeber erfragen.

# Supabase (Produktion oder lokale Instanz)
NEXT_PUBLIC_SUPABASE_URL=https://[projekt-id].supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...

# App-URL (lokal)
NEXT_PUBLIC_APP_URL=http://localhost:3000

# E-Mail via Resend
SMTP_HOST=smtp.resend.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=resend
SMTP_PASS=re_...
SMTP_FROM_NAME=BODYTIME concept
SMTP_FROM_EMAIL=onboarding@resend.dev
RESEND_API_KEY=re_...

# Cron-Job Absicherung
CRON_SECRET=...

Entwicklungsserver starten

npm run dev
# → http://localhost:3000

Build prüfen

npm run build
npm run start

Umgebungsvariablen

In Produktion ausschliesslich in Coolify gesetzt. Lokal in .env.local.

Variable Sichtbarkeit Bedeutung
NEXT_PUBLIC_SUPABASE_URL Client + Server Supabase Projekt-URL (öffentlich, kein Secret)
NEXT_PUBLIC_SUPABASE_ANON_KEY Client + Server Supabase Anon Key (öffentlich, durch RLS abgesichert)
SUPABASE_SERVICE_ROLE_KEY Nur Server Umgeht RLS komplett – nur in Server Actions / Route Handlers verwenden
NEXT_PUBLIC_APP_URL Client + Server Basis-URL der App (z.B. https://bodytime-concept.de) – wird für Bestelllinks genutzt
SMTP_HOST / PORT / USER / PASS Nur Server Nodemailer-Konfiguration für Resend SMTP
SMTP_FROM_NAME / FROM_EMAIL Nur Server Absender-Name und -Adresse in ausgehenden E-Mails
RESEND_API_KEY Nur Server Resend API-Key (redundant zu SMTP – für direkten API-Zugriff)
CRON_SECRET Nur Server Bearer-Token zur Absicherung des Cron-Endpoints /api/cron/reminders

Wichtige Architektur-Prinzipien

Das Projekt folgt dem Next.js App Router-Modell strikt:

  • Server Components sind der Standard – kein "use client" ohne Grund
  • Alle Datenmutationen laufen über Server Actions in src/actions/
  • Client Components nur für Interaktivität (Formulare, Modals, Animationen)
  • Supabase RLS schützt alle Daten auf Datenbankebene
  • Der Service-Role-Key wird nur in vertrauenswürdigen Server-Kontexten genutzt

Middleware / Auth-Schutz

Datei: src/proxy.ts (wird als Next.js Middleware über middleware.ts im Root eingebunden).

Routing-Logik

MARKETING_ROUTES → immer durchlassen
/, /b2b, /bestellung, /beratung, /danke, /datenschutz, /impressum – kein Auth-Check
PUBLIC_ROUTES + eingeloggt → Weiterleitung zum Dashboard
/login, /register etc. – wenn Session aktiv, zum passenden Dashboard
PROTECTED_ROUTES + kein Login → /login
/partner/*, /admin/* – ohne Session redirect zu Login mit ?redirect=
Role-Check → falsches Dashboard → redirect
Partner auf /admin/* → /partner/dashboard und umgekehrt
Deaktivierter Account → ausloggen + /login?deactivated=1
Session wird gelöscht, alle sb-* Cookies entfernt
ℹ️
Neue öffentliche Routen müssen zu MARKETING_ROUTES in src/proxy.ts hinzugefügt werden, sonst werden sie als "unbekannte Route" behandelt (404 oder Auth-Redirect).

Code-Patterns

Supabase-Client – welcher wann?

FunktionWo nutzenDatei
createClient() Server Components, Server Actions, Route Handlers lib/supabase/server.ts
createAdminClient() Server Actions die RLS umgehen müssen (z.B. Admin-Aktionen) lib/supabase/server.ts
createBrowserClient() Client Components ("use client") – nur lesen lib/supabase/client.ts

Server Action Beispiel

'use server';
import { createClient } from '@/lib/supabase/server';
import { revalidatePath } from 'next/cache';
import type { ActionResult } from '@/types';

export async function updateSomething(data: FormData): Promise<ActionResult> {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) return { success: false, error: 'Nicht eingeloggt' };

  const { error } = await supabase
    .from('bt_table')
    .update({ field: data.get('field') })
    .eq('id', user.id);

  if (error) return { success: false, error: error.message };

  revalidatePath('/partner/...');
  return { success: true };
}

Deployment

Automatischer Deployment-Flow

1. git push origin main
Jeder Push auf den main-Branch startet den Prozess
2. GitHub Actions (.github/workflows/)
CI/CD-Pipeline: Build-Check + Webhook-Call an Coolify API
3. Coolify zieht den Code
Coolify klont das Repository, baut das Docker-Image mit npm run build
4. Container-Neustart
Alter Container wird gestoppt, neuer gestartet. Zero-Downtime durch Coolify-Proxy

Manuelles Deployment (Notfall)

Im Coolify-Dashboard auf "Redeploy" klicken. Oder via SSH auf dem Server:

ssh root@178.105.172.209
# Coolify-Container-ID herausfinden und manuell redeployen
docker ps

E-Mail & Cron

E-Mail-Versand

Alle E-Mails laufen über Resend via SMTP (smtp.resend.com:587). Der Versand-Code liegt in src/lib/email/mailer.ts, Templates in src/lib/email/templates.ts.

Folgende E-Mails werden versendet:

AuslöserEmpfängerTemplate
Partner einladen (Admin)Neuer PartnerEinladungslink
Passwort vergessenUserMagic Link (Supabase nativ)
Kontaktformular ausgefülltAdminKontaktanfrage
Vertrag läuft in 30/14 Tagen abPartnerErinnerungs-E-Mail (via Cron)

Cron-Job: Vertragserinnerungen

Endpoint: GET /api/cron/reminders – muss täglich mit dem korrekten Bearer-Token aufgerufen werden.

# Aufruf (z.B. via Coolify Cron oder externem Dienst)
curl -H "Authorization: Bearer [CRON_SECRET]" \
  https://bodytime-concept.de/api/cron/reminders

Der Job prüft alle Kunden auf Vertragsenden in den nächsten 30 und 14 Tagen und sendet je eine E-Mail an den zuständigen Partner. Gesendete Erinnerungen werden in bt_reminder_logs gespeichert.

Admin-Workflows

Neuen Partner anlegen

/admin/partners → "Partner einladen"
Name + E-Mail-Adresse eingeben
Supabase sendet Invite-E-Mail
Partner erhält Link, setzt Passwort über /invite
Partner kann sich einloggen
Profil in bt_profiles mit role=partner, is_active=true

Steckbrief freigeben

Partner reicht Steckbrief ein
Status wechselt auf pending
/admin/freigabezentrale
Admin sieht alle pending Steckbriefe
Freigabe oder Ablehnung mit Begründung
Status → approved (sichtbar auf Landingpage) oder rejected (mit Feedback)

Gutschein-Code ändern

/admin/settings – der Code wird als Sentinel-Eintrag in bt_documents mit dem Key __setting:voucher_code__ gespeichert. Alle Partner sehen sofort den neuen Code auf ihrer Bestellseite.

Partner deaktivieren

/admin/partners/[id] → "Deaktivieren". Setzt is_active=false in bt_profiles. Der Partner wird beim nächsten Request automatisch ausgeloggt (Middleware prüft is_active bei jeder Anfrage).
